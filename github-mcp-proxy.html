What a gateway does that a token can't

The moment you hand an agent an MCP server, you hand it every permission the credential behind that server holds. A worked example of closing that gap: per-tool authorization by identity, roles that are a matter of policy rather than credentials, per-identity rate limits, and PII redaction on what tools return.

PART 1

Over-privilege is the default, not the exception

Picture an engineering agent — a developer's desktop assistant, a coding agent in the IDE, an internal bot — wired to a self-hosted MCP server for your source control platform. It lists issues, reads files, searches code, reads pull requests. It also creates and updates files.

The moment you hand that server to a caller, the caller inherits everything the credential behind it can do. Read and write, one token, no line between them, and no independent record of who did what. That is over-privilege by default — and it has the same shape whether the caller is a person or an agent acting on their behalf.

This is not a source-control problem. It is the shape of every MCP server you put in front of an agent, and it is the reason "we gave the agent an MCP server" and "we govern what the agent can do" are two very different sentences.

The fix is to move the decision.

Stop asking the credential to express authority it was never designed to express, and let the gateway decide instead — per tool, per caller, default-deny. Then add the two controls a token has no concept of at all: a cap on how much a caller can do, and a screen on what comes back.

Tools are not equal, but a token can't tell them apart

An MCP server exposes tools, and those tools carry wildly different risk. Listing issues, reading a file, searching code and reading a pull request are all reads. Creating or updating a file is a write that lands in your repository.

A personal access token doesn't care which caller is asking. It carries a fixed set of scopes, and every caller behind it gets all of them. No per-caller distinction, no default-deny, no independent audit trail. That is the hole: one credential's worth of authority, handed to everyone who reaches the server.

PART 2

One governed endpoint, one policy model

Putting a Gravitee MCP Studio in front of the server changes four things at once. None of them require the upstream MCP server to learn anything new.

Identity

The caller brings its own identity

Each caller authenticates as itself and maps to a group — Admin, Engineering, Triage. The agent is no longer anonymous behind a shared secret.

Credential

The upstream credential never leaves the gateway

Callers never hold it, so it can't leak from a config file on a laptop — and you rotate or revoke it in exactly one place.

Enforcement

Every tool call is an authorization decision

Evaluated as a subject (the caller), an action, and a resource that names the specific tool being invoked.

Default

Default-deny

A tool call with no matching permit is refused. Nothing is allowed by omission — the safest possible failure mode.

Curation is a control, not a convenience

A studio also composes. Rather than wiring an agent to three raw MCP servers with three credentials, you expose one vetted endpoint carrying only the tools you approve, drawn from only the servers you approve — source control alongside a documentation server, an internal knowledge tool, whatever the job actually needs.

That curation is a security control in its own right. The tools you never expose are tools no policy has to defend against, and the agent's blast radius shrinks before authorization is even consulted.

PART 3

Authorization per tool, per identity

Policy is written in Cedar, so the rules are readable by the people who have to sign off on them. A read-mostly Engineering role takes two statements — a broad permit, and a targeted forbid on the one tool that writes:

// Engineering may use every tool...
permit(principal in Group::"engineering", action, resource);

// ...except the write, which is forbidden.
// In Cedar, forbid always beats permit.
forbid(principal in Group::"engineering", action,
       resource == MCPTool::"github-mcp-server.create_or_update_file");

That last line is worth sitting with. Forbid always beats permit, so a broad grant can never accidentally re-open a tool you have explicitly closed — no matter how many policies get added later, or by whom. That property is what makes a policy set safe to grow.

The result, driving the same studio as two different callers:

Caller (group)list_issuesget_file_contentssearch_codepull_request_readcreate_or_update_file
bobEngineering
 PERMIT PERMIT PERMIT PERMIT FORBID
aliceAdmin
 PERMIT PERMIT PERMIT PERMIT PERMIT

Same agent, same server, same upstream credential. Four reads allowed, one write refused — and the refusal happens at the gateway, before the call ever reaches the upstream server. The write comes back 403 with no upstream call made at all.

The audit trail is the second deliverable

Enforcement is the obvious win. The decision record is the one that matters to your auditor, because every call leaves a line naming the caller, the tool, the outcome, and the policy that decided it:

subject=User::"…bob…"  action=github-mcp-server.list_issues
  decision=PERMIT  reason="Permitted by policy 'engineering-can-use-tools'"

subject=User::"…bob…"  action=github-mcp-server.create_or_update_file
  decision=FORBID  reason="Forbidden by policy 'engineering-forbid-create_or_update_file'"

A shared token cannot produce that record, because at the moment of the call there is no per-caller identity left to write down. This is the difference between "the agent had access" and "here is who asked, for what, and why the platform said yes."

PART 4

Roles become a matter of policy, not credentials

Read-versus-write is the coarse cut. The valuable one is narrower: a triage or support agent that reads issues and searches code, and can do nothing else at all. One statement enumerates exactly what it may touch:

permit(principal in Group::"triage", action, resource)
when { resource == MCPTool::"github-mcp-server.list_issues"
    || resource == MCPTool::"github-mcp-server.search_code" };

Everything without an explicit permit falls through to deny — so this role is defined by what it can do, and the list is two items long:

Callerlist_issuesget_file_contentssearch_codepull_request_readcreate_or_update_file
trishTriage
 PERMIT DENIED PERMIT DENIED DENIED
The point worth taking away

Three tiers — Admin, Engineering, Triage — over one server and one credential. Each tier is a difference of policy, not a difference of token. Nobody minted a new credential, nobody scoped a second PAT, and nobody has to remember which secret is the "safe" one. Adding a fourth role tomorrow is a policy change, reviewable in the same way you review anything else.

PART 5

Governing how much, not just what

Here is the failure mode authorization alone will not catch: a compromised or looping agent doesn't need a forbidden tool to cause damage. It can hammer a perfectly permitted one. Agents retry. Agents loop. An agent that decides to search your codebase four thousand times is behaving entirely within policy.

So cap it. A rate limit on the studio flow, keyed on the caller's identity rather than on the connection or the source address, gives every identity its own budget:

bob → list_issues, calls  1–10 : allowed   (200)
bob → list_issues, calls 11–13 : throttled (429)

Keying on identity is the whole trick. A global limit protects the upstream server but lets one runaway agent consume everyone's headroom. A per-identity limit contains the blast radius to the caller causing it — one agent hitting the wall doesn't touch anyone else's budget, and the identity in the throttling record tells you immediately which agent to go look at.

PART 6

Governing what comes back

Authorization decides whether a read is allowed. It says nothing about what that read returns — and with agents, the return path is the one that should worry you. A permitted file read on the wrong file hands an agent, and the model behind it, a customer's name, email address and phone number. From there it flows into a context window, possibly a log, possibly a third-party model provider.

So screen the response. A PII filtering policy scans what the tool returns and redacts the categories you nominate — names, emails, phone numbers, financial and government identifiers, locations. Take a support file that genuinely contains a customer's contact details. Read through a governed endpoint, this is what the agent actually receives:

Customer: [REDACTED]
Email:    [REDACTED]
Phone:    [REDACTED]
Notes: follow up on the double-charge dispute.

Name, email and phone masked. The line the agent actually needs — the dispute note — passes through untouched, so the agent stays useful. Redaction that destroys the answer isn't a control, it's an outage.

Why in-gateway inference matters here

The classification model runs inside the gateway. The payload is never shipped to an external service just to be inspected — which would mean solving your data-exposure problem by creating a second one. The data stays inside your boundary for the entire round trip.

PART 7

Why the platform's own controls don't close this

It's a fair question — source control platforms do give you knobs. It's worth being precise about how far they reach, because they are genuinely useful and genuinely not sufficient.

  • Token scopes limit the token, not the caller. Every caller behind that token shares its authority. Scopes are a ceiling on the credential; they can't distinguish your triage agent from your admin.
  • Server-wide read-only mode is all-or-nothing. It applies to everyone connected. You either lose write for the agents that legitimately need it, or keep it for the agents that shouldn't have it.
  • Neither produces an independent decision record. There is no per-caller, per-tool audit trail naming the policy that decided the call, because there is no per-caller identity at that point in the chain.
  • Neither has any concept of a per-identity rate cap or a redaction screen. These are properties of the call path, not of the credential — so they can only be enforced by something sitting on that path.

The practical answer is both, not either. Set the platform-side controls tightly — that's your ceiling. Then let the gateway express the per-caller authority the credential was never able to describe.

PART 8

The pattern, not the product integration

Nothing described here is specific to source control. Every control in this walkthrough operates on the MCP call itself — the identity making it, the tool being invoked, the rate it arrives at, the payload coming back. None of them reach into the upstream server's internals, which is exactly why the same model transfers.

Swap the server and keep the model: one governed endpoint, one policy set, one rate cap keyed on identity, one screen on the response path. Ticketing systems, internal databases, CRM, observability, a homegrown service someone wrapped in MCP last week — the shape doesn't change.

  • Move the decision to the gateway. Per tool, per caller, default-deny — the credential was never the right place to express who may do what.
  • Make roles a policy concern. Three tiers over one credential beats three credentials nobody can keep straight.
  • Cap how much, not just what. Agents loop; per-identity limits contain the caller responsible instead of everyone around them.
  • Screen the return path. An allowed read is not the same as a safe response, and the return path is where sensitive data reaches the model.

Agents are going to keep asking. The question is what answers back.

Every one of these controls exists because an agent is an unusually enthusiastic caller of things you have already exposed. The gateway is where the platform gets to have an opinion about that — per subject, per tool, default-deny, with a record of every decision.

Source control is simply the first box. The box is replaceable.

A good place to start is the narrowest agent you have. Give it one identity, one role, and the shortest list of tools that still lets it do its job — then widen deliberately. The estate that follows is easier to govern than the one you inherit.
