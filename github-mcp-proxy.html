Governing a GitHub MCP server with Gravitee: what one gateway does that a token can't

One Gravitee MCP Studio in front of a self-hosted GitHub MCP server, doing four things the GitHub token can't: per-tool authorization by identity, a narrow read-only role, per-identity rate limiting, and PII redaction on tool responses. Real policy, live proof for every claim, and an honest look at where it stops.

PART 1

What you're securing, and the shape of the fix

Take an engineering agent — a developer's Claude Desktop, a Cursor agent, an internal bot — wired to a self-hosted GitHub MCP server. It lists issues, reads files, searches code, reads PRs. It also creates and updates files. The moment you hand that server to a caller, the caller inherits everything the GitHub token behind it can do. Read and write, one credential, no per-caller line between them, no independent record of who did what. That's over-privilege by default, and it's the same shape whether the caller is a person or an agent acting for one.

Make the gateway decide — per tool, per caller, default-deny.

I put one Gravitee MCP Studio in front of that server, then added a rate cap and a PII screen on top. This is the policy, the config, and the proof, captured live: a write from a read-only agent dies at the gateway, a runaway agent gets throttled, and a name and email in a file come back redacted before the agent ever sees them. Not a slide.

The hole in a token

A GitHub MCP server exposes tools, and tools are not equal. list_issues, get_file_contents, search_code and pull_request_read read. create_or_update_file writes. GitHub's own token doesn't care which caller is asking — a personal access token carries a fixed set of scopes, and every caller behind it gets all of them. No per-caller line, no default-deny, no independent audit. That's the hole: one credential's worth of authority, handed to everyone who reaches the server.

The architecture — one studio, one policy model

Identity

The caller holds its own identity

An OAuth token from Access Management, mapped to a group — alice → Admin, bob → Engineering, trish → Triage.

Credential

The GitHub credential lives only in the studio

The caller never holds it, and you rotate or revoke it in one place.

Enforcement

Every tool call is an authorization decision

Evaluated at the gateway as a subject (the caller), an action, and a resource that names the specific tool.

Default

Default-deny

A tool call with no matching permit is refused. Nothing is allowed by omission.

The studio also curates: in this build it exposes nine tools drawn from several upstream servers behind one endpoint — the GitHub server plus a docs server, a Q&A tool, and a network tool. The agent connects to one vetted, governed endpoint instead of wiring itself to three raw MCP servers with three credentials. Curation is a control in its own right: only the tools you approve, from the servers you approve. Standing up the GitHub MCP server itself — container, token, scopes — is GitHub's own procedure and out of scope here.

PART 2

Authorizing per tool, per identity

Policies are Cedar, authored as GLOBAL and deployed to the engine:

POST .../modules/authz/policies   {"name":…, "kind":"GLOBAL", "policyType":"MCP", "policyText":…}
POST .../modules/authz/policies/{id}/deploy
A correction, because getting it wrong once and saying so is more useful than a quiet fix

My first instinct was to author this through the console — create an MCP-scoped policy, pick the studio from a list. That list came up empty, even with the studio deployed, its tools present, and a published plan. Verified again live this session. What works is authoring the Cedar directly. Whether the empty picker is an alpha indexing gap or a step I missed is unconfirmed, and worth a code check before it's stated as product behavior.

The three policies that produce a read-mostly Engineering role, by name from the live decision log:

// Engineering may use every tool...
permit(principal in Group::"<engineering>", action, resource);

// ...except the write, which is forbidden. In Cedar, forbid always beats permit.
forbid(principal in Group::"<engineering>", action,
       resource == MCPTool::"github-mcp-server.create_or_update_file");

// Admin gets everything.
permit(principal in Group::"<admin>", action, resource);

PART 3

Narrowing to a triage tier

Read-versus-write is the coarse cut. The finer one is a role that can barely do anything — a triage or support agent that reads issues and searches, and nothing else. One policy, a when clause enumerating exactly the two tools it's allowed:

permit(principal in Group::"<triage>", action, resource)
when { resource == MCPTool::"github-mcp-server.list_issues"
    || resource == MCPTool::"github-mcp-server.search_code" };

Everything without an explicit permit falls through to deny. Live, as trish (Triage):

Callerlist_issuesget_file_contentssearch_codepull_request_readcreate_or_update_file
trishTriage
 PERMIT DENIED PERMIT DENIED DENIED

Three tiers now — Admin, Engineering, Triage — over one server and one credential, each a difference of policy, not of token.

Sync subtlety worth knowing

A brand-new identity's group membership is pushed to the decision engine asynchronously, so the very first call after you create the user can miss its permit until the sync settles. Give it a beat.

PART 4

Capping the agent — per-identity rate limiting

A compromised or looping agent doesn't need a forbidden tool to do damage — it can hammer a permitted one. So cap it. A rate-limit policy on the studio flow, keyed on the caller's identity, gives each identity its own budget:

{ "policy": "rate-limit",
  "configuration": {
    "addHeaders": true,
    "rate": { "limit": 10, "periodTime": 60, "periodTimeUnit": "SECONDS",
              "key": "{#context.attributes['user']}" } } }

That key is the whole trick. The MCP flow exposes the caller as {#context.attributes['user']} — the same attribute the authorization policy keys off — so the limit is per identity, not global. Live, bob capped at 10 per 60 seconds:

bob list_issues call  1–10 : allowed   (HTTP 200)
bob list_issues call 11–13 : throttled (HTTP 429)

Governance on how much, not just what. One caller hitting the wall doesn't touch anyone else's budget.

PART 5

Redacting what comes back — PII on tool responses

Authorization decides whether a read is allowed. It says nothing about what the read returns. get_file_contents on the wrong file hands an agent — and the LLM behind it — a name, an email, a phone number. So screen the response. This needs two pieces: a token-classification model resource, and a filtering policy that uses it.

// resource: an on-gateway PII model
{ "name": "pii-model", "type": "ai-model-token-classification",
  "configuration": { "model": { "type": "GRAVITEE_BERT_SMALL_PII_DETECTION" } } }

// policy: scan responses, redact the matched categories
{ "policy": "pii-filtering",
  "configuration": {
    "resourceName": "pii-model",
    "categories": ["PERSON","EMAIL","PHONE","FINANCIAL_ACCOUNT","GOVERNMENT_ID","LOCATION"],
    "threshold": 0.5,
    "skipResponsePayloadFiltering": false } }

I proved it against a real file. contact.txt on a branch of the demo repo really contains Jane Smith, jane.smith@example.com, +1-415-555-0142. Read through the governed studio, here's what the agent actually receives:

Customer: [REDACTED]
Email:    [REDACTED]
Phone:    [REDACTED]
Notes: follow up on the double-charge dispute.

Name, email and phone masked. The non-PII line — the dispute note — passed through untouched. The model runs inside the gateway, so no payload leaves the boundary just to be classified.

One honest catch — found by trying, not by reading

The PII model is CPU-bound and runs per response. When I flooded the studio with rapid calls to test the rate limit, the gateway started throwing VertxException: Thread blocked and returning 502s — the model was blocking the event loop under the flood. At normal request rates it's fine, and a paced call stream returns clean.

But size it for your traffic, and treat "PII-screen every response, at any concurrency" as a thing to load-test, not assume. It's a real reason to want the inference off the request thread, and worth raising with the AIM team.

PART 6

Boundaries — GitHub's own controls, and where this stops

Why not just use GitHub's own controls

Fair question — GitHub gives you knobs. Be precise about where they reach. PAT scopes limit what the token can do, but per token, not per caller — every caller behind that token shares the same authority. The MCP server's read-only mode is server-wide, all-or-nothing for everyone connected. Neither gives you a single, default-deny policy authored once, evaluated per calling identity, per tool, with an independent decision record the GitHub side never produces — let alone a per-identity rate cap or a PII screen on what comes back. That's the gap the studio fills.

The GitHub-side controls here are third-party context — set them tightly, but they're a different layer.

Where it stops today

  • Authorization is tool-level, not argument-level. I wanted "permit writes to a sandbox repo, forbid production," and it can't be expressed here. I probed it live: the enforcement point passes only the tool name to the policy, never its arguments — a forbid conditioned on any of repo/branch/owner/path in the policy context never triggered, and the Cedar schema is empty. Tool-level is the real, working boundary. Argument-level would need the engine to pass tool arguments to the policy — a roadmap ask.
  • PII filtering blocks under a flood (above). Suited to normal request rates.
  • LLM proxies don't expose the same fine-grained-authorization toggle that MCP studios do in this build — an LLM proxy needs the enforcement added by hand.
  • The aim module is alpha (alpha.129). Behavior can move between builds.

The pattern, not just GitHub.

Nothing in any of this is GitHub-specific. The gateway decides per subject, per tool, default-deny; caps per identity; and screens what comes back — on any MCP server it fronts. Swap the server, keep the model: one governed endpoint, one Cedar policy set, one rate cap, one PII screen, per-caller authority the underlying credential can't express on its own.

GitHub is the first box. The box is replaceable.
