A single architecture story for a regulated property & casualty carrier: retire the platform risks that are capping the roadmap, then unlock governed AI on the same runtime that already carries the transaction traffic.

The through-line

Your platform shape is capping your roadmap.

Every operational pain traces back to the self-hosted deployment, and every stated ambition — high availability, Universe, Agent Management — is blocked by it. The migration is not three purchases stacked together; it is one architectural move that retires risk and removes a ceiling at the same time.

Single point of failure — infrastructure

One database takes down everything

The entire control plane — the console and the Management API — goes offline when the on-premises MongoDB goes down. The cloud backup is not a true failover. A control plane that dies with one database is a Single Point of Failure (SPOF).

Single point of failure — people

One person owns the platform

Every upgrade, patch, implementation, and the overdue high-availability work all run through a single administrator. That concentrates all platform risk — and all delivery bandwidth — in one person.

PART 1

Target architecture — hybrid-first, managed control plane

Keep the data plane where it belongs, move the control plane to managed. The gateways stay on-premises for latency, data residency, and InfoSec comfort — the things a regulated carrier cannot compromise on. Gravitee Cloud takes over the control plane, which removes the single-database failure point and lifts the upgrade/patch burden off the one administrator.

Active-active HA — the scoping question to put on the table

Active-active across cloud and on-prem is a stated goal, and the managed control plane removes the Single Point of Failure that has blocked it. But whether active-active is delivered in this migration or sequenced as a follow-on is an open question scoping has to answer — it depends on their routing and requirements, not on the licence. Put these on the table in the scope call:

  • Routing — the gating item. The redundant-gateway redesign has been stalled 2+ years on undocumented NetScaler / NGINX routing with no container documentation. Active-active cannot be designed until that is documented and re-architected. Is that reverse-engineering in this migration's scope?
  • Shared state — confirm the Redis answer. Active-active distributed rate limiting and quota need shared state — the highly-available Redis Enterprise they ruled out as too costly. Confirm how the target provides it before committing to an active-active design.
  • Cross-site gateway pool — in scope or phase two? A cloud gateway pool running alongside the on-prem pool is what makes it active-active across locations. Decide whether that stands up in this migration or is sequenced later.
  • Residency requirements — capture them. Which traffic must stay pinned on-prem (via sharding tags / tenants) versus can use either pool? That is a requirement to pull from their InfoSec and architecture team, not an assumption to make for them.

Recommended framing for the scope call: confirm whether active-active is in scope for this migration. If yes, the routing re-architecture is the critical path and everything else follows from it. If not, the migration still retires the control-plane risk today, and active-active becomes a clean phase-two deliverable on the same foundation.

Critical path — own this in scoping

The redundant-gateway work has been stalled for 2+ years because traffic routes through undocumented NetScaler and NGINX configuration with no container documentation to work from. That routing is the migration's critical path — reverse-engineering and documenting it during scoping is what unsticks a two-year problem and earns credibility with the architecture team. The target design must account for it explicitly, not assume it away.

PART 2

Agent Management — reference architecture

A regulated carrier cannot run ungoverned AI. The requirements the enterprise-architecture team wrote are not a wish list — they are a governance specification, and they map almost one-to-one onto Agent Management. The reference architecture is the same control-plane pattern used for the API estate, one protocol layer up: identity in front, policy in the middle, catalog as the source of truth, full lineage out the back.

Talk track — layer by layer

Agent IdentityCIMD · SPIFFE/SPIRE · hosted

"Without identity, every other control collapses." Desktop agents authenticate via Client ID Metadata Document bound to the human's enterprise single sign-on; workloads (CI, workflow steps) get short-lived, auto-rotating SPIFFE credentials with an hour-bounded blast radius. A leaked key in a config file has unbounded blast radius — this is the answer to the risk every security lead is already worried about.

AI GatewayLLM · MCP · A2A, one runtime

One enforcement point for all agent traffic — same authentication, policy, and observability chain across model calls, tool calls, and agent-to-agent delegation. The LLM Proxy also delivers real-time cost attribution by team and use case — the answer to the CFO's inevitable "how would we even know what we're spending?"

Authorization ManagementFine-Grained Authorization · Cedar

Policy is written against real catalogued entities, not opaque strings — "deny delete_repository on that MCP server for this agent" is a one-line policy. The decision engine runs inside the gateway, so authorization is on the hot path with no network hop. This is the layer that turns "we adopted AI" into "our CISO signed off on it."

Catalogthe source of truth

The bridge to ten years of accumulated integration work: an existing REST API becomes an API Tool, a Kafka topic becomes a Kafka Tool, an internal document becomes a Resource — all agent-accessible without redevelopment. The mainframe wrapper nobody wants to touch never learns MCP; the Catalog absorbs the heterogeneity.

MCP StudioComposite MCP servers

Don't expose eight raw MCP servers to one agent. Compose the exact toolkit that agent needs — a curated set of tools, resources, and prompts with PII redaction and per-call authorization — as a named, versioned, governed artifact. This is curation as a security control, not just convenience.

Observability & lineagecost · alerts · audit

"You can't govern what you can't see." Every hop is traced with identity, tool, latency, policy decision, and cost, stitched into a navigable graph — the complete audit trail for the moment a regulator or customer asks "did your AI agent see my data?" Their existing Alert Engine is already the on-ramp here.
